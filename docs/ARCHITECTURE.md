# Kiến trúc BrewLite

Frontend Next.js App Router, TypeScript, Tailwind CSS và CSS token của `stitch/**/DESIGN.md`. `app/` chỉ điều phối màn hình; `components/` chứa shell, auth provider, thành phần UI và tóm tắt; `stores/cart.ts` dùng Zustand persist; `types/domain.ts` giữ hợp đồng chung; `services/` chứa interface, mock và REST adapter. `NEXT_PUBLIC_DATA_MODE=mock|hybrid|api` chọn adapter tĩnh (`hybrid`: products + cart dùng REST, các module còn lại mock); lỗi API không tự chuyển sang mock. Auth luôn gọi backend thật.

Backend NestJS modular monolith: `auth/` đăng ký, đăng nhập, cookie JWT, guard và role; `products/` đọc PostgreSQL; `orders/` và `inventory/` của TV4 tạo đơn, giữ kho và điều khiển trạng thái. Staff Orders đã có list/transition, còn thiếu detail/hủy có lý do/lịch sử. Payments có core nhưng chưa nối Orders port; Promotions/Loyalty chưa có backend. Prisma quản lý schema/migration/seed. Password băm bcrypt, role lấy từ DB khi xác thực. Cookie HttpOnly, SameSite=Lax, Secure khi NODE_ENV=production, path `/api`; middleware kiểm tra Origin cho các lệnh ghi bằng cookie. JWT mang `sessionVersion` đối chiếu với `users.session_version` trên mọi request; logout tăng version rồi xóa cookie, làm hết hiệu lực mọi phiên của user. Auth response có `Cache-Control: no-store`.

Giỏ và đơn demo lưu localStorage theo browser; session khôi phục qua GET `/auth/me`. Backend không dùng dữ liệu demo. Orders thật tạo PENDING với giá backend tính lại và snapshot item trong transaction giữ kho. `POST /payments` mới xác nhận PAID/PAYMENT_FAILED; UNKNOWN giữ trạng thái chờ xác minh. Mock ghi idempotency key và giữ giỏ khi thanh toán thất bại. Barista frontend có KDS 5 view; Staff API dùng `JwtAuthGuard` + `RolesGuard` và không tự fallback về mock khi API mode lỗi.

Ảnh sản phẩm mock lấy URL gốc trong HTML Stitch; truy cập ảnh gốc cần mạng trên trình duyệt; SVG tĩnh dự phòng khi offline. Ảnh sản phẩm seed API lấy SVG tĩnh ở `frontend/public/images/products`.

OrdersModule dùng AuthModule + PrismaModule + InventoryModule. Tạo đơn tính giá từ catalog, chụp snapshot, giữ kho và lưu history trong một interactive transaction. Inventory dùng optimistic locking Product.version cùng điều kiện stock >= tổng qty theo product. Transition dùng Order.version và state machine, release/re-reserve trong cùng tx; OrdersService export hàm nhận transaction để TV5/TV6 ghi payment/loyalty nguyên tử. StaffOrdersController nằm trong OrdersModule và tái sử dụng đúng service này; không thay endpoint mẫu `/barista/dashboard` của TV1. Quy tắc cụ thể và giới hạn ở `API_CONTRACT.md`.
